# Pulse on Runpod Serverless, update: network volume, hosted APIs, streaming latency

Ashwin Sreedhar, 2026-09-27. Follow-up to the 2026-09-23 write-up. Raw data: `results.csv` (cold-start rows from 15:53 ET on), `bench/logs/vol_*.log` (worker logs), `bench/quality.csv` batches `ecd7d2ad` and `9a0ac311`, and `pagedserve/results/hosted_*.json` (streaming sweeps, run with the load generator from my inference-engine project). Friction log entries #41 to #48.

## 1. Cold starts with a network volume: the volume never mounted

The plan was the before/after that the Sep 23 breakdown pointed at: put the HF cache and vLLM's compile caches on a network volume so a cold start skips the 15 s download and the ~30 s torch.compile. Setup: new worker-vllm endpoint (`kbme98hqtjthdl`, template v2.27.2, vLLM 0.30.0), 50 GB volume `pulse-vllm-cache` in EUR-IS-1, `VLLM_CACHE_ROOT`, `TORCHINDUCTOR_CACHE_DIR` and `HF_HOME` all under `/runpod-volume`, confirmed in the release. Four measured starts:

| start (ET) | GPU | delayTime | container start to healthy | weight download | torch.compile |
|---|---|---|---|---|---|
| 16:24 | A100 PCIe | (worker started by the deploy) | 141 s | 15.0 s | 32.5 s |
| 16:32 | A100 PCIe | 173.0 s | 142 s | 14.5 s | 32.9 s |
| 16:43 | H100 SXM | 152.7 s | 144 s | (log truncated) | 34.0 s |
| 17:02 | H100 SXM | 147.6 s | 138 s | 12.8 s | 33.0 s |

Nothing changed between starts. Every log shows the weights downloaded again and `Filesystem type for checkpoints: OVERLAY`, even with `HF_HOME` pointed at the volume; every log shows torch.compile running in full and "saved AOT compiled function" to the volume path, never a load. After the four starts I listed the volume over Runpod's S3 API: 0 objects. A probe object wrote and listed fine, so the listing works. `/runpod-volume` inside these workers was the container's own overlay directory, not the attached volume, and everything written there died with each container.

So the before/after doesn't exist yet; what exists is a reproducible failure with logs. Two side results from the same runs: an H100 and an A100 start in the same 138 to 144 s, so this startup is CPU and I/O bound, not GPU bound; and the warm scoring call is 1.22 to 1.29 s for 64 tokens on both (~50 tok/s), the same as the RTX 4090 last week (51 tok/s).

The afternoon also added to the placement story. The first attempt, RTX 4090 in EU-RO-1, hit a host that looped `error creating container ... exit status 1` every two seconds with no backoff, and after terminating it nothing placed for 13 minutes; 4090 availability then went N/A in every datacenter. On the working endpoint, terminated workers stayed listed as idle/ready in `/health` for three-plus minutes while the container was already removed, and the next request paid a full start each time (173 s, 148 s). One `delayTime` of 241 s was reported on a request the worker log shows served in 2 s.

Two things I'd want to know from the Runpod side: whether volume mounts are expected to work on worker-vllm Serverless endpoints in EUR-IS-1 (the S3 listing says the mount never happened), and whether `/health` is meant to report a terminated worker as ready.

## 2. Qwen3-8B on Serverless against the hosted APIs

Same 50-article Pulse fixture as before, Claude Haiku 4.5 as the reference. New this week: DeepSeek V4.1 Flash and Kimi K3 through OpenRouter, both with reasoning switched off (with it on, DeepSeek spent 121 output tokens per article and only 16 of 50 answers parsed; off, 28 tokens and 50 of 50).

| model | where | exact | within 1 | urgent P / R | $ per 1,000 | wall p50 |
|---|---|---|---|---|---|---|
| Claude Haiku 4.5 | Anthropic API | ref | ref | ref | $0.74 | 1.13 s |
| Claude Sonnet 4.6 | Anthropic API | 76% | 100% | 100 / 67 | $2.09 | 1.79 s |
| Kimi K3 | OpenRouter | 76% | 98% | 82 / 100 | $1.95 | 1.41 s |
| DeepSeek V4.1 Flash | OpenRouter | 52% | 98% | 75 / 67 | $0.03 | 0.98 s |
| Qwen3-8B bf16, prefix caching | Runpod, A40 | 46% | 90% | 64 / 78 | $0.021-0.032 batched (c32-c64), $0.13 at c8 | 1.61 s |
| Qwen3-32B-AWQ, prefix caching | Runpod, A6000 | 38% | 86% | 42 / 56 | $0.041 batched (c32) | 1.71 s |
| qwen3:8b Q4 | local Ollama, M1 Pro | 38% | 90% | 58 / 78 | $0 | 1.55 s |

Cost per 1,000 uses OpenRouter's listed prices on the day ($0.0348 / $0.60 per M tokens for DeepSeek Flash, $3 / $15 for Kimi K3) at the fixture's real token counts (~450 in, ~30 out).

The Qwen comparison holds: the 8B is cheaper and closer to Haiku than the 32B, so model size isn't the lever on this task. What's new is the column next to it. DeepSeek Flash lands at the same cost as my cheapest self-hosted configuration, with better agreement (98% within one point against the 8B's 90%), no cold start, and nothing to operate. For Pulse's volume, that's the honest recommendation unless the data has to stay in-house. Kimi K3 is the best open-weight quality I've measured, Sonnet-level on every metric, but at list price on OpenRouter it's Sonnet-priced too, 2.6x Haiku per article; I don't know what rate you're getting for it, and that would change the picture.

## 3. Streaming latency, all systems from the same load generator

ShareGPT first-turn prompts (median 37 tokens), 128-token cap, streamed, measured from my Mac. Kimi and Haiku ran at 0.3 req/s because a new OpenRouter account is capped at 20 requests a minute for those models.

| system | rate | TTFT p50 / p99 | TPOT p50 / p99 |
|---|---|---|---|
| Runpod, Qwen3-8B bf16, H100, `/openai/v1` | 1 req/s | 771 / 1,545 ms | 8.3 / 17.8 ms |
| same | 4 req/s | 923 / 1,344 ms | 8.2 / 15.5 ms |
| same, 100 simultaneous, 1 worker | burst | 63.6 s / 292 s | 8.1 / 20.8 ms |
| DeepSeek V4.1 Flash, OpenRouter | 1 req/s | 723 / 1,588 ms | 4.1 / 7.9 ms |
| same | 4 req/s | 960 / 2,208 ms | 5.1 / 8.4 ms |
| Kimi K3, OpenRouter | 0.3 req/s | 889 / 3,310 ms | 14.0 / 28.8 ms |
| Claude Haiku 4.5, OpenRouter | 0.3 req/s | 936 / 1,761 ms | 7.8 / 12.8 ms |

Two Runpod-specific things in there. The `/openai/v1` route costs about half a second of first-token latency that the queue route doesn't: on the same warm H100 worker, `runsync` from my Mac spent 264 to 355 ms outside execution (wall minus executionTime, queue delay 50 to 58 ms), while the streaming route's TTFT p50 was 771 ms, and the model's prefill on a 37-token prompt is ~10 ms. And the route doesn't absorb a burst: 100 simultaneous streams on one worker (MAX_CONCURRENCY 64) fell to 36.9 tok/s total, against 359 tok/s at 4 req/s, with a 64 s median first token and 4 dropped streams, while TPOT stayed at 8 ms, so the GPU wasn't the bottleneck. For Pulse the queue route is the right one for scoring calls, and batches should go through it at ~30 in flight.

## What I'd do next

Get an answer on the volume mount, because the compile cache is the one thing that would take a cold start from ~140 s to under 100 s on this image. Until then, the cost model from Sep 23 stands: Serverless works for Pulse if it wakes a few times a day and batches, and a hosted API at $0.03 per 1,000 is the comparison it has to beat.
