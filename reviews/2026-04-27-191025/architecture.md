# Architecture Review · 2026-04-27

## TL;DR
The three-tier architecture is intact: zero `ipcRenderer` calls in the renderer, zero `src/main/` imports in `src/renderer/`/`src/preload/`, no DB access outside main, IPC channel names line up between preload and handlers. The boot sequence is the most procedurally complex thing in the codebase but it's self-consistent. There are no Critical findings. The notable structural debts are (1) `ollamaService.ts` has grown into a 2.2K-line god-module mixing client/queue/health with prompt logic for ~14 distinct features, (2) IPC handler registration is unevenly split across `index.ts:registerIpc` and `ipc/handlers.ts:registerDbIpc` with no rule explaining the split, and (3) `aiClient.ts` is an incomplete abstraction — it only routes 3 of the ~14 Ollama call sites, so most callers still bypass it.

## Critical
None.

## Important

- **[src/main/services/ollamaService.ts:1-2244]** — Service has accreted 14 unrelated prompt families (urgency scoring, company description, hyper intent, hyper Q&A, feed suggestion, personal brief, graph edge classify, customer concentration, new-node classify, value-chain generation, earnings-release summary, ticker-news summary, sector classify, plus the health-check/queue infra) into one file. New AI features are added by appending another `export async function …` here, so the boundary keeps eroding. The queue + concurrency limiter (`MAX_CONCURRENT = 2`) is shared globally across all 14 callers, so a single backed-up flow (e.g. `regenerateAllChains` on the watchlist) starves urgency scoring and hyper Q&A — by inspection, only `enqueueOllamaTask` goes through the queue, and most of the 14 functions call `fetch` directly without queuing, so the bound is partial and inconsistent.
  - **Why it matters:** any future contributor reaching for "the right place to add a new Ollama prompt" lands on a file where the answer is "tack it on the end". The shared singletons (`lastHealthCheckAt`, `healthy`, `healthListeners`, the implicit unbounded direct-fetch path) make it difficult to reason about throughput or to swap the backend for a single feature. Compare with `claudeService.ts` (1203 lines) which has the same problem at smaller scale.
  - **Fix:** keep `ollamaService.ts` as the *transport* layer (health, queue, raw `chat()`/`completion()` helpers, model name, status emitter) and split each of the prompt families into its own `prompts/<feature>.ts` that imports the transport. Mechanically this is a series of cuts — no behavior change, no change to call sites until you choose to. Bias for moving the largest functions first (`generateCompanyValueChain`, `summarizeEarningsRelease`, `generatePersonalBrief`) since each is >100 lines and self-contained.
  - **Fix safety:** 🟢 Safe.

- **[src/main/index.ts:436-457] vs [src/main/ipc/handlers.ts:143]** — Two IPC registration sites with no documented rule for which channel goes where. `registerIpc` in `index.ts` owns `app:*`, `prefs:apply`, `feeds:refreshAll`, `hyper:applySettings`, and the four `reels:*Status` channels; `registerDbIpc` in `ipc/handlers.ts` owns everything else including other `prefs:*`, `feeds:probe`, and `db:reels:*`. The split is inconsistent: `db:prefs:get` is in handlers but `prefs:apply` is in index; `db:reels:list` is in handlers but `reels:piperStatus` is in index. The only thing the in-`index.ts` handlers have in common is that some close over locals (`popoverWindow`, `markMainRendererReady`).
  - **Why it matters:** when adding a channel, "where does it go" requires reading both files. A future contributor will pick the closer one, deepening the inconsistency. There's also a subtle correctness risk: `registerIpc` runs before `registerDbIpc`, so any future cross-handler dependency (e.g. "this handler needs a window opener that's set in the other") is order-sensitive without that being stated.
  - **Fix:** move all five `reels:*Status` handlers and `feeds:refreshAll`, `prefs:apply`, `hyper:applySettings`, `app:getOllamaStatus` into `ipc/handlers.ts`, taking the locals they need (`popoverWindow`, `markMainRendererReady`, `applyPreferences`) as injected parameters. Leave only the few that genuinely need raw access to module-scoped main-process state inline. Drop `registerIpc`; rename `registerDbIpc` to `registerIpc`.
  - **Fix safety:** 🟢 Safe.

- **[src/main/services/aiClient.ts:208-293]** — The "single chokepoint for AI provider routing" only covers 3 of the ~14 Ollama call sites: `generateCompanyValueChain`, `classifyTickerSectors`, `answerQuestion`. Every other consumer (`feedPoller`, `personalRelevance`, `discoveryService`, `tickerSummaryService`, `smartLookupService`, `feedFinderService`, `companyProfileService`, `earningsReleasesService`, `graphCandidatesService`, `graphNotesRefreshService`, `tenKConcentrationService`, `reelService`, `hyperDispatcherService`) imports from `ollamaService` directly. As a result, the cap counter / Claude fallback never fires for those paths even when `aiProvider='claude'` is configured.
  - **Why it matters:** the user-facing semantics of `aiProvider='claude'` are "use Claude where Claude is wired up" — but there's no way for the user to know which 3 routes are wired up vs the 11 that aren't. Worse, the next time someone adds a Claude variant for one of the un-routed flows (e.g. earnings-release summarization in claudeService — which already has `summarizeEarningsRelease`?), they'll have to thread it through aiClient and risk forgetting the cap counter.
  - **Fix:** either (a) rename `aiClient` to `aiRoutedCalls` (or similar) so it's clear the abstraction only covers a subset, OR (b) inventory which calls *should* go through it and which legitimately should not (urgency scoring is a hot loop and may not want Claude cost). This is a documentation/scope clarification, not a behavior change.
  - **Fix safety:** 🟢 Safe (scope clarification only — no behavior change unless a follow-up decides to route a call).

## Nice-to-have

- **[src/main/services/aiClient.ts:60, 111-127]** — `CAP_GATE_DISABLED = true` constant with extensive conditionals around it. The current code path: `recordClaudeCall` is still invoked from `pickProviderForCall` flows but skips persistence and console warnings when the gate is disabled. The `resetClaudeUsage` IPC and Settings UI for the cap remain reachable. This is fine *now* because it's a deliberate kill-switch (per recent commit `3b7de0d` "Disable Claude daily cap pending budget evaluation"), but the constant is invisible to anyone debugging "why isn't the cap working".
  - **Why it matters:** a future user reading the code expects `DAILY_CLAUDE_CAP = 50` to mean what it says.
  - **Fix:** add a single comment at the top of the file (above the `const`) referencing the commit message and what re-enabling looks like ("flip CAP_GATE_DISABLED to false; recordClaudeCall will start persisting again"). No code change.
  - **Fix safety:** 🟢 Safe.

- **[src/main/services/feedPoller.ts:58-61, 79]** — When a poll is already in-flight, `pollAllFeeds` returns a *fake empty PollSummary* (`{ feedsPolled: 0, articlesInserted: 0, ... }`) rather than awaiting the in-flight one. The renderer's `feeds.refreshAll()` path (App.tsx:155) shows the user a stale state if they hit Refresh while a poll is running. Same shape applies to the deferred-poll branch at line 79.
  - **Why it matters:** the user sees "0 new articles" when the actual in-flight run might be ingesting hundreds. Low impact (the broadcast `feeds:polled` event still fires when the in-flight run finishes), but the IPC return value is semantically wrong.
  - **Fix:** keep an in-flight `Promise<PollSummary>` reference at module scope; when re-entering, return the same promise so the caller awaits the real result. Or document that the IPC return is best-effort and not a precise signal.
  - **Fix safety:** 🟢 Safe (refactor only — broadcast pathway already covers the renderer's actual UI update).

- **[src/main/index.ts:716-748]** — Splash watchdog uses `Promise.all([feedsP, stocksP, ollamaP, kokoroP, piperP, videoP, mediaToolsP])` plus a 180s `setTimeout` cap, but `void backfillArticleTickerMatches()` and `setTimeout(() => void prefetchAllCompanyProfiles(), 5_000)` are fire-and-forget *outside* the splash gate. If the user's first-run experience needs those completed (the comment at line 736-737 says exactly that — "otherwise Today's brief would be empty"), the gate isn't actually gating them.
  - **Why it matters:** today's brief on first boot can be empty for a few seconds even after the splash hands off. Probably acceptable, but the comment suggests intent that the code doesn't enforce.
  - **Fix:** either move `backfillArticleTickerMatches()` into the awaited Promise.all (it's already a Promise), or update the comment to match reality ("brief may render empty for a few seconds on cold start"). Pick one.
  - **Fix safety:** 🟡 Bug *if* the backfill is meant to gate the splash — pure 🟢 Safe if the comment is the thing that's wrong. User decides which is the right resolution.

## Skipped (intentional given Pulse's nature)

- **App.tsx is 6391 lines** — explicitly intentional per CLAUDE.md ("App.tsx is ~5000 lines and owns all top-level routing"). Components are extracted where there's reuse; remaining length is the routing/feed-list/reader composition.
- **Two-hooks-only renderer (`useArticles`, `useCategories`)** — most state is local to App.tsx. Personal-tool framing makes Redux/Zustand-style hoisting a tax, not a benefit.
- **`ollamaService.ts` re-exports types via `index.ts` indirectly** — fine for a single-tenant local app.
- **`stopMaintenanceSchedule` does not interrupt an in-flight `runMaintenance`** — the function is synchronous and short (no awaits inside the SQLite calls), so reentrancy is bounded by the duration of a single VACUUM. Acceptable.
- **No CONTRIBUTING.md, public API docs, test pyramid** — explicitly skipped per agent guidance.
- **Dynamic `await import(...)` for half a dozen services in handlers.ts and index.ts** — looks like splitting for boot-time savings; not a smell, but worth noting that this also defers any throw-on-import from those modules to first IPC call rather than to boot.
